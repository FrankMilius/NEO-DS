Form Field

Universeller Wrapper für Label + Input + Hint + Error. Kombiniert alle Form-Bestandteile zu einer zusammenhängenden Einheit. Kanonische Klasse: .nc-form-field (BEM). Enthält .nc-form-label, .nc-form-hint und .nc-form-error.

Default Form Field

Standard-Aufbau: Label, optionaler Hint, Input und optionale Error-Message. Vertikal gestapelt.

Mindestens 3 Zeichen, nur Buchstaben und Zahlen.

Error State

Modifier .nc-form-field--error propagiert den Fehlerstatus auf den enthaltenen Input und zeigt die .nc-form-error Nachricht an.

Bitte geben Sie eine gültige E-Mail-Adresse ein.

Horizontal Layout

Mit .nc-form-field--horizontal werden Label und Input nebeneinander angeordnet (ab Tablet-Breakpoint).

Verschiedene Input-Typen

Das Form Field funktioniert mit allen Eingabetypen: Input, Textarea und Select.

Maximal 500 Zeichen.

Accessibility Referenz

Form-Field-Komponenten verbinden Labels, Hints und Errors semantisch mit dem zugehörigen Input-Element.

aria-describedby Verlinkung

  • Jeder Input muss über aria-describedby mit seinen Hint- und Error-Elementen verlinkt sein
  • Hint und Error erhalten eindeutige id-Attribute (z.B. hint-email, error-email)
  • Mehrere IDs werden durch Leerzeichen getrennt: aria-describedby="hint-email error-email"
  • Das Label wird über for/id verlinkt — nicht über aria-describedby

role="alert" auf Fehlermeldungen

  • Jede .nc-form-error muss role="alert" haben, damit Screenreader den Fehler sofort vorlesen
  • Alternativ aria-live="polite" für weniger dringliche Validierung
  • Der Input selbst erhält aria-invalid="true" im Error-State
  • Bei dynamischer Validierung: Fehlermeldung erst nach Interaktion einblenden (nicht sofort bei Seitenladung)

Required-Indikator

  • Das visuelle Sternchen .nc-form-label__required erhält aria-hidden="true"
  • Die programmatische Pflichtfeld-Information kommt über aria-required="true" am Input-Element
  • Screenreader lesen “required” automatisch vor — das Sternchen ist nur visueller Hinweis
  • Alternativ: required HTML-Attribut am Input (native Validierung)

Label-Zuordnung

  • Jeder Input braucht ein zugeordnetes <label> mit for="input-id"
  • Das Label muss sichtbar sein — aria-label allein genügt nicht als Ersatz (WCAG 2.4.6)
  • Klick auf das Label fokussiert den zugehörigen Input (native Browser-Funktionalität)
  • Im Horizontal-Layout bleibt die for/id-Verlinkung identisch

Welche Form-Komponente?

Semantische Entscheidungslogik (Faustregeln) für die Wahl der richtigen Form-Komponente basierend auf Datentyp und Auswahlmodus.

1 Boolean-Wert? (Ja/Nein, An/Aus)
Ja
Checkbox Zustimmung, Opt-in, AGB
Switch Setting mit sofortigem Effekt, z. B. Dark Mode
Nein ↓
2 Einzelauswahl, wenige Optionen (2–5)?
Ja
Radio Group Alle sichtbar, vertikale Liste
Segmented Control Kompakt, 2–4 kurze Labels
Nein ↓
3 Einzelauswahl, viele Optionen (6+)?
Ja
Select Standard-Dropdown, ≤20 Optionen
Combobox Sehr viele Optionen oder Suche nötig
Nein ↓
4 Mehrfachauswahl?
Ja
Checkbox Group Wenige (≤7), alle sichtbar
Multi-Select / Tag Picker Viele Optionen, platzsparend
Nein ↓
5 Numerischer Wert?
Ja
Number Input + Stepper Exakter Wert: Menge, Alter, PLZ
Slider Ungefährer/kontinuierlicher Wert — Wert immer sichtbar machen!
Nein ↓
6 Datum oder Uhrzeit?
Ja
Date/Time Input + Picker Keyboard-first! Tastatureingabe + optionaler Picker kombinieren
Nein ↓ Fallback
7 Keiner der obigen Fälle?
→
Text Input Freitext (Fallback)
